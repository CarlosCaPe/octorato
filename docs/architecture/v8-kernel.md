# Octorato v8: The Kernel

> v7 made a send without receipts impossible. v8 makes an agent run a process: identified, isolated, replayable, and installable like a service.

## 1. What "kernel" means in v8

ROADMAP.md:5 says Octorato wants to be "the kernel they run on"; ROADMAP.md:17 admits it "is not yet a runtime with its own kernel". RFC #0002 (ROADMAP.md:23) is decided today: Octorato stays a governance layer that compiles to harnesses (docs/architecture/multi-runtime.md:4-14), and the kernel is a **contract enforced by hooks, scripts and git**, implemented first on Claude Code 2.1.x and portable by binding rows. The kernel is four primitives every run passes through: PROCESS (a run has a pid, parent, worktree, quota and exit status), ISOLATION (one writer per tree and per file lane, denied not advised), JOURNAL (an append-only, hash-chained, replayable record per process, refusals included) and PACKAGE (skills carry a signed, semver manifest with a tree hash, a tracked lockfile, and verify at doctor and pre-push time; arms are validated and installed, not signed). It is NOT a runtime binary, NOT a scheduler, NOT a message bus, and NOT a daemon: the process table is a locked JSON file (the `connectome/sessions.json` pattern, session-isolation-hook.py:52-75, octo-dim.py:52-62), liveness is read from journal mtimes, and the only periodic work rides the existing `brain-digest` systemd user timer (install-observability-timer.py:29). Two things this shape cannot do, stated plainly: it cannot kill or suspend a running agent (hooks cannot block `SubagentStart`; a breached quota denies every later tool call, so **processes can be starved, not killed**), and it cannot schedule. Both are M4 and stay out of scope.

Registry ids, existing categories (rules.schema.json:31): `ARCHITECTURE.kernel-process`, `ARCHITECTURE.kernel-isolation`, `FLOW.kernel-journal`, `FLOW.kernel-quota`, `META.kernel-package`. ARCHITECTURE cannot sit at PRESENCE (rules.schema.json:84-86); META can, so `META.kernel-package` is declared GATE explicitly.

Runtime facts every phase obeys: same-event hooks run in parallel, so no phase assumes hook order; a PreToolUse call is denied when ANY hook denies; `PermissionDenied` is documented for auto-mode denials only; the ptable is written outside the hot path (SessionStart, SubagentStart, SubagentStop, CLI) with one exception, a NEW lane claim on a first write, amortized once per path per process, under the same flock and counted in `octo bench`; every writer goes through `kernel_proc.py` under flock plus `os.replace`.

Existence (who may open a journal): a process comes into being in exactly two places, `register()` from the SessionStart and SubagentStart reflexes, and the hot-path gate when a first tool call beats its own register hook (the call IS the process's first trace, which is why the gate never denies on a missing `start` line). An ENDING is not one of them. `append()` creates the journal it writes to, so `r__subagent-stop__proc-exit.py` checks `kernel_proc.has_trace(pid)` (a journal on disk, or a ptable row) and records nothing for a pid the kernel never saw. The harness fires `SubagentStop` for agent ids that never registered, never ran a tool and never produced a transcript; without that check each one materialised a whole process out of a single line, a journal whose only record was an `exit` at seq 0 with no parent and no tool (52 such files in one afternoon, measured). A journal with no ptable row is still shown by `octo top`, with type `?`, never as `main`: `top` reads the disk as well as the table, so it must not claim a type the kernel never learned. Orphan journals are swept by `prune_files()` on the same `PRUNE_AFTER` window as every other journal, and no sooner: the journal is the audit trail, and a shorter window for the files that record an anomaly would delete the evidence of it.

What a trace is, and what the guard costs. A trace has to be evidence of WORK, so a zero-byte journal and a ptable row whose value is not an object are both refused: the first is reachable only from a crash between the create and the first write, the second because `pid in procs` tests the key alone. The row half of that is UNREACHABLE through today's read and is kept as defence in depth, which is a weaker claim than the one this paragraph used to make: `read_ptable` drops a value that is not an object before `has_trace` sees it, so the lookup returns `None` whichever predicate is written there (QA measured it). It stays because it is the same predicate the read applies, at the point of use, for a caller that ever reaches it with a table that did not come through the seam, and the anchor for it hands in exactly such a table. The phantom stops are identifiable at the source too, measured over 90 of them: they carry no `agent_type` and a non-empty final assistant message, and they arrive on a periodic cadence near 32 s rather than tracking tool calls, which reads as a harness-internal side-call surfacing as `SubagentStop`. The guard has one cost, stated plainly because a check that trades one bug for a worse one is not a fix: if a real `SubagentStop` ever landed BEFORE its own `SubagentStart` for a child that ran zero tools, its exit would be dropped and the row would read live until the 900 s TTL. Measured on this machine that window is not reachable: register leads the child's first tool call by 4.45 s to 12.77 s across every real child, the shortest real child lived 55 s, and the register hook itself runs in 50 to 100 ms. The cost is bounded anyway, because `claim_lane` creates the row it needs, so a row-less toolless child holds no lane; what expires late is a liveness reading, not a lock. `has_trace` is off the hot path (only the stop reflex calls it) and costs 48 us with the journal present. The row-shape half of that guard is no longer `has_trace`'s alone: QA measured that one value which is not an object took down `octo ps`, `octo top`, `octo replay`, two `brain_doctor` checks and BOTH register hooks, the last of them silently, because `prune()` raised inside the ptable lock and the hook still exited 0. So the shape is decided once, at the read: `kernel_proc.sane_table` DROPS a value that is not an object and `read_ptable_detail` hands the dropped pids back, so `octo ps`, `octo top` and the doctor name what went missing (a repair nobody can see is its own failure mode) and every locked writer republishes the table without it. A read never writes. That read reports at TWO levels, because they are not the same event, but they are the same VERDICT and QA cycle 4 is why the difference had to shrink to reporting. A dropped ROW costs n named rows; a FAULT is `processes` itself not being an object and costs every row on the machine, unnamed and uncounted (QA measured the same rows rewritten as an array and the isolation gate, reading an empty table as "nobody owns anything", ALLOWED the second writer onto a held lane and let the write that followed republish a one-row table with the intruder holding it). The old claim that a row-level drop "leaves a table you can still trust" does not survive n being ALL of them, one row at a time: corrupting only the HOLDER's row left `fault` empty, both gates allowed, and the next `register` republished the table without that row, so the lane was gone for good. So both gates deny on a drop, `claim_lane` refuses on one, the doctor FAILs on one, and `_publish` carries it forward like a table-level fault; what stays two-level is the message, which names the pids when it can.

Zero rows is the truth about a machine in exactly one state, and the state is about the MACHINE rather than the file: no journal beside the table reads live, and the journals themselves can be walked. **How** the file reached zero rows does not enter into it. That is a correction, not a restatement: the guard used to key on `FileNotFoundError`, so it covered a DELETED table and nothing else, and three cheaper moves walked past it (writing `{"version":1,"processes":{}}` over the file, corrupting every row's value, corrupting one row's value). All three yielded zero rows from a file that exists, all three read as a fresh install, and the reader contradiction this section cites as its own proof reproduced verbatim: `octo ps` said "the kernel has registered nothing on this machine yet" while `octo top` listed four live processes out of the same directory. Any other way of yielding zero rows is a machine whose table somebody else made unreadable or removed, so it is never read as a fresh install. The gates fail CLOSED on it (a gate that cannot read the table cannot know whether a lane is held, and one writer per tree is fail-closed), the listings print it above the table instead of announcing an empty machine, and the doctor FAILs rather than WARNs.

Three more of the same shape, and one residual. A PARSE that fails is a fault whatever the parser calls the failure: `json.load` on 20 KB of nested `[` raises RecursionError, which is neither `ValueError` nor `OSError`, so it escaped every fault leg and left through the gates' outer `except Exception: sys.exit(0)` as rc=0 with empty stdout, empty stderr, no deny, no journal line and no quarantine, which is strictly quieter than the deletion above; the reader catches it by shape and each gate additionally denies around its one ptable read, while staying fail-open for every other exception, where allowing the call is the right failure. A ptable path that is NOT A REGULAR FILE is a fault before it is opened: `os.path.getsize` succeeds on a fifo and `open` then blocks forever, and both gates were still running at 60 s, which is neither fail-closed nor fail-open but a hung session. A `lanes` that is not a list of paths makes its ROW unreadable: `lanes_of` coerced a string, a null or a list of numbers to `[]`, so the row stayed in every listing looking healthy and silently forfeited the path it held. And a JOURNAL the kernel did not delete is a record somebody removed, not a process that ended: `rm journal/<holder>.jsonl` freed the holder's lane with the table intact, so a colliding row whose journal is missing holds its lane, and `prune` keeps that row and faults the table instead of freeing it (bounded by PRUNE_AFTER, so a fault nobody clears still expires; `recovery()` names the row as the thing to delete, because there the row is the evidence). chmod, truncation and garbage in that journal already blocked; only deletion was permissive.

The residual is that the journals are evidence stored in the directory the attacker is reaching. An unreadable journal directory, or a file where it belongs, is unambiguous and faults. A journal directory that is simply GONE is not, so it faults only when the kernel directory still shows the machine has run hooks (`.ptable.lock`, a quarantine copy, `open-pending.json`, anything a writer left). **Stated plainly: an attacker who removes the whole kernel directory leaves a HOME that is byte for byte a wiped cache, and no reader can tell those apart from inside.** That is a strictly larger move than the one this closes, it is measured and allowed on purpose (denying every fresh install is the broken-laptop failure), and it sits beside the interpreter path `recovery()` already documents. Two smaller ones, in the same spirit: a fault whose cause is a missing journal is cleared by deleting the ROW rather than the `_faulted` key, since clearing the key alone re-faults at the next prune; and two SessionStart hooks racing on a machine whose table has never existed can read each other's brand-new journals as "somebody else is running", which is a false fault bounded by one registration and unchanged by this cycle. `_publish` is the one function that replaces the file, so it copies what it is about to overwrite to `~/.claude/.cache/kernel/ptable.corrupt-<utc>.json` first, with the reason and the raw bytes: the lost rows stay readable, the repairs are countable (the doctor escalates on three in 24 h, frequency rather than presence), and the copy is taken at the WRITE, so a reader that repairs in memory and writes nothing still leaves no file. That closed the other half QA found: `octo ps` prunes on read, prune is a writer, so on the normal steady state of one old dead row the listing silently rewrote the file without the corrupt row and the footer that was meant to name it read `dropped == []`.

How long a fault lasts, and how it ends. A fix that only fails closed until the next write is a fix that lasts minutes: `register` publishes even on a faulted table (a hook exiting 0 with no row on disk is the silent failure the seam exists to stop), and it used to publish `fresh_table()` plus its own row, so the fault went with the write. QA measured the whole sequence with the real gate and the real SessionStart hook: denied while faulted, one register later the rows on disk read `['newsess']`, the fault read `''`, the same intruder was ALLOWED and the lane the other process held was transferred to it. SessionStart fires on startup, resume, clear and compact. So the row is still published and the empty base is not: `sane_table` hands back a table carrying the unreadable value under `_faulted` (reason, timestamp, the count, and a bounded slice of the rows, which in the list-shaped case are intact and each carry their own `pid`), every writer republishes it, and `carried_fault` keeps reporting it. Ownership stays UNKNOWN: nothing reads those carried rows as lanes, `claim_lane` keeps refusing, both gates keep denying and the doctor keeps FAILing, for as many registrations as it takes. The way out is a file operation from a terminal where no hook fires, `rm ~/.claude/.cache/kernel/ptable.json` (the next SessionStart rebuilds it, and every lane held right now is forgotten until each process claims again) or repairing `processes` to an object and deleting the `_faulted` key beside it, which keeps the rows the file still has. Deliberately NOT an `octo` subcommand and not an env hatch: a fault denies every hooked write, so a command that clears it is a command the agent can run to clear its own gate, which is the `--release` reasoning taken one step further. Every deny, both listings and the doctor print that recovery, from one string in `kernel_proc.recovery()` so they cannot drift.

Which unreadable, and which absent. QA cycle 3 measured two holes in the paragraph above and both were in the SHAPE of the guard, not its intent. First, `read_ptable_detail` had two `except OSError` legs and they disagreed: the one on `open` carried the fault, the one on the `getsize` above it returned `fresh_table()`. Which leg an unreadable table lands on is chosen by whoever made it unreadable (a directory at the path fails at `open`, an ELOOP symlink fails at the stat), so through the stat leg the whole loss reproduced verbatim, down to zero quarantine files for the doctor to count. Both legs carry now and the anchor is written with a symlink loop. Second, and larger: the attacker's cheap move is not corruption, it is DELETION, and both reach the file through the same door (`rm`, `mv` and a `>` redirect at the kernel directory are denied by the Bash gate; `python3 -c` and `ln -sf` are not, which `test_named_residuals_are_honestly_uncovered` already pinned). Corruption buys a deny-all the attacker also suffers. Deletion bought a silent allow-everything machine: no fault, no copy, no doctor FAIL, no deny, while `octo ps` printed "the kernel has registered nothing on this machine yet" and `octo top` listed two live processes out of the same directory. So an ABSENT table is a fault when any journal beside it reads live by the definition above, and the one honest empty table is an absent file with nothing live next to it. The carve-out is a single explicit argument: `register` writes its own journal before it takes the ptable lock, so it passes its pid to `read_ptable_detail` and that one journal does not count, or every fresh install would fault on its first SessionStart. The cost is one documented step in the recovery, stated there rather than discovered: after the `rm` the machine stays faulted until the next SessionStart writes a table or those journals go quiet.

What the recovery says, and what it may claim. The text used to describe the file's PRE-register shape while the deny it is attached to only persists into the POST-register one, so by the time a human read it "repair `processes` to an object" was a no-op and the only actionable half left, "delete the `_faulted` key", discarded every row the fault carried; QA followed it literally and reproduced the lane transfer. It now describes the post-register state, names `_faulted.rows` as where the carried rows are and the `ptable.corrupt-*.json` copy as where the original is, and says what deleting the key alone costs. The reason for having no subcommand is stated as what is VERIFIED rather than as a fact: the direct file verbs are denied, and the interpreter path is open and measured. Closing that is a real expansion of the Bash gate's verb detection with its own false-positive risk and it is deliberately its own change.

Fixtures, because the counts have to be able to move. The fail-closed fault branch could be deleted from BOTH gates and both selftests still passed with identical counts (3+2/29 and 16+13/5) while `brain_doctor` reported that both isolation gates prove themselves: no fixture covered the branch, so no count could move, and a count that did not move looks exactly like a count that was checked. There are now six, a pair per gate per cause: an unreadable table that must block, a deleted table that must block, and a genuinely fresh install that must ALLOW. The benign leg is what makes the violations mean anything, since without a table that is empty for an honest reason "denies when it cannot read the table" and "denies" are the same measurement. A fixture carries its own kernel state through `_setup.ptable` and `_setup.journals`, because a faulted table cannot be the shared seed. New counts: 18+14/8 and 5+3/32, and deleting the branch now fails both.

What a repair is allowed to cost. The ledger's bound used to be a count of files, and the size of each one is chosen by whoever wrote the corrupt table: QA measured a 46.1 MB ptable producing a 47.7 MB copy, 245 MB of peak RSS, 1.64 s of it INSIDE the ptable lock, and a 20-file worst case near 954 MB. Three bounds now, all in `kernel_proc`: `MAX_PTABLE_BYTES` (8 MiB) is checked with a stat BEFORE the parse, so a table past it is a fault that is never parsed, which is what takes the big read out of the lock window (every locked writer parses through that read); `MAX_QUARANTINE_BYTES` (1 MiB) caps what one copy preserves, recorded as `truncated` next to the original `bytes` so a partial copy is never mistaken for a complete one; `MAX_QUARANTINE` (20 files) and `MAX_QUARANTINE_TOTAL` (8 MiB) bound the ledger together, newest always kept; and a copy older than `PRUNE_AFTER` goes on the register-path sweep, because bounded by count and bytes alone a copy never expired at all and one corruption held the doctor at WARN forever while nothing told the operator where the files were or that removing them was safe (`recovery()` now says both). The record also names WHO: the kernel `pid` the writer acts for, plus `os_pid` and `argv0`, because the process that overwrote every lane on the machine used to leave `ts`, `reason` and the bytes and nothing identifying itself. One copy per EVENT, not per write: the carrier remembers the copy it already has, so carrying a fault forward does not refill the ledger or trip the doctor's three-in-24 h escalation off a single corruption.


How a fault ENDS, which until cycle 5 was a question this file could not answer. `FAULT_KEY` was written by four places, read by two, and removed by NONE: no `pop`, no `del`, on any path. Measured on the F4 lost-lanes fault: `recovery()` prescribes deleting the ROW, QA deleted the row, and the machine stayed faulted before AND after the next register, so the gate printed an instruction the operator had just executed; the blast radius is machine-wide, because one dropped row denied a write to a tree no row had ever touched. Every bound this file claimed for a fault was a bound on something ELSE, and the second measurement proved it: a faulted row aged past `PRUNE_AFTER` pruned, the lane freed, `_faulted` stayed and the deny stayed. So a fault now says what KIND it is and the reader re-derives the ones that can be re-derived (`fault_resolved`). `latched` is a table whose rows were lost: their count is unknown and nothing on disk can say what they held, so only a human clears it, which keeps the F1 protection exactly as sticky as it was. The other three are conditions and end when the condition does. `lost-lanes` names the rows, and it lifts when they are removed, when their journals come back, or when prune expires them. `journal-evidence` lifts when the directory is usable again. `zero-rows` names the pids whose journals read live when the table lost its rows, and lifts when they exit or go quiet, by which time the lanes it was protecting are moot. `carried_fault` stops reporting a resolved one and `_publish` removes the key from the file, so the two readers stop printing a fault whose condition is gone. `recovery()` takes the kind and prints the branch that WORKS for it, which is the other half of the same finding: one text listing every option is the text that told the operator to delete a key which, for this fault, re-faults on the next prune.

Two SessionStart hooks on a table-less machine used to brick it permanently, and the trigger is a first run with two terminals. `register` writes its journal BEFORE it takes the ptable lock (deliberately: published-then-written let a sibling prune delete a row whose journal did not exist yet), so the first hook to take the lock reads an absent table with the sibling's brand-new journal beside it and faulted, and before the paragraph above nothing could ever clear that. It is also the state the documented `rm ptable.json` recovery puts the machine into, so recovery could loop. The fix uses the kernel's own doctrine, `has_trace`'s "a trace has to be evidence of WORK": `live_journal_pids` now ignores a journal that carries only `start` lines, because a registration in flight holds no lane (`claim_lane` creates the row it needs and runs off a tool call), and two registers serialize on the ptable lock anyway, so the second reads the first's published row instead of losing it. It weakens nothing real: a process that has WORKED carries a `tool` line, and journal content cannot be forged without breaking the hash chain. The residual is named: a lane claimed in the window between `claim_lane` and that process's own first journal line would not count, which is one tool call wide and only on a process's first tool call, against a permanent machine-wide lockout.

Liveness reads the CHAINED RECORD, not only the mtime, because F4 was one syscall deep. `lane_owner` guarded DELETION (`_mtime is None`) and `_own_fresh` was mtime-only, so one `touch` on a live holder's journal freed its lane with nothing deleted, nothing edited and the chain intact: `live_journal_pids` returned `[]`, both gates ALLOWED, while the last record in that file said the process was seconds old. That is F4's own sentence, "a missing liveness record selecting the permissive branch", applied to a BACKDATED record instead of a removed one, and the enumeration it shipped with ("chmod, truncation and garbage already blocked; only deletion was permissive") was missing the fourth member of its own list. `touch` is already in the Bash gate's kernel-state verb list, so the threat model named the move before the reader did. `_quiet_for` is now the one definition of "how long has this been quiet", read by `_own_fresh` (TTL) and by `prune` (PRUNE_AFTER), because prune read the raw mtime too and backdating a week dropped the row outright at the next SessionStart without the lane check ever being consulted. The honest claim: this raises the price of faking death from one metadata syscall to rewriting the last line of a hash-chained file, and it is not unforgeable. The direction it can still be wrong in is the safe one, since an mtime touched FORWARD keeps a lane held and expires at PRUNE_AFTER rather than handing it to a second writer.

The wipe residual was understated, and the guard was keyed on the syscall one level up. `journal_evidence_fault` consulted `_kernel_has_history()` only on the `FileNotFoundError` leg, so it covered the journal directory being GONE and said nothing about it being EMPTY or STALE. Four cheaper states allowed on both gates with `.ptable.lock` present and every history marker intact: `rm ptable.json journal/*.jsonl` (the directory stays), a written-empty table plus the same sweep, and either of those with the journals BACKDATED instead of removed. The last two are closed by the chained record above. The first two are closed here, keyed on the result: an EMPTY journal directory on a machine whose kernel state says hooks have run is a sweep, because `register` writes its own journal before it takes the lock, so the kernel cannot produce that state. The stated objection does not apply, since a real fresh install has no kernel directory at all and `_kernel_has_history()` is False on it. What that costs, said rather than discovered: after a week of idleness `octo ps` can prune the last journals without registering one, and the next read faults until any SessionStart writes a journal. A quiet machine is one whose journals are OLD, not one with none. The one residual that stands is unchanged and is still the larger move: removing the whole kernel directory leaves a HOME that is byte for byte a wiped cache.

A damaged journal directory with an INTACT table is a fault too, and it used to be described wrongly rather than missed. F3's fault only ran on the zero-rows path, so a directory that was gone, replaced by a file, unreadable or swept beside a healthy table produced a LANE deny naming a dead pid as "never journaled" and advising the operator to "wait for that process to exit", which cannot happen: silence is measured out of the file that is missing. It is reachable by any cache sweep over `~/.claude/.cache`. `read_ptable_detail` asks the question on every read now, at the cost of a `stat` and an `access` rather than the old `os.listdir` (the directory's size is chosen by whoever writes it), and the rows are left exactly where they are, since the fault is about the evidence and not about them. `lane_recovery` is the other half: a lane held by a row with no journal beside it does not free on silence, and both gates now say so and name what to restore.

The in-code labels ran `QA cycle 3..6` while HEAD's own commit message called the last set `QA cycle 4`, so grepping either number found half the record. They are renumbered to the commit message's line, per PR: cycle 1 = the review that produced `f5a480b`, 2 = `bb4d374`, 3 = `6c760e7`, 4 = `2672773` (F1, F1c, F2, F3, F4, F5, F6), 5 = the review that produced C1-C4 and M1-M2 above. Liveness (one definition, used by every gate): main process live = its own journal mtime, or any child's journal mtime, within TTL 900 s (session-isolation-hook.py:48), so a parent waiting on a long child never reads dead; subagent live = no `exit` line AND parent live AND own journal mtime within TTL 900 s, so a killed or hung agent expires after 15 minutes and releases its lanes (a single Bash call is capped by the harness well under that, so an active child never expires). ### Phase 2: ISOLATION, one writer per tree and per lane, enforced

Goal: the weekend failure becomes a violation fixture. A process cannot touch a path the journal attributes to a different live process, parent included, and cannot write into another arm.

A write, a destructive git verb, or a Bash mutation targeting a path whose lane belongs to a DIFFERENT live process is denied (a parent-owned tree does not license a sibling to touch a sibling's file; and a parent RELEASES its own lanes when it spawns a child, journaled as `release` with reason `delegate`, so an edit-then-delegate on the same file is not self-denied, while a parent lane claimed after the spawn still binds); lane matching is equality or path prefix, so `rm -rf <dir>` is denied when any other live lane sits under `<dir>`. ## 5. Risks and the decisions only the operator can make

Risks: (1) A single Python hook on `PreToolUse *` costs about 80 to 100 ms per call on the reference box (interpreter 33 ms, stdlib imports 66 ms); the bench is reported, never gating, and journal + quota stay ONE invocation. (2) Two process tables (`sessions.json`, ptable) for one release; the lane fix lives in the ptable only, and the merge is v8.1 debt. (3) Cursor cannot project SubagentStart, PermissionDenied or Agent-scoped events (multi-runtime.md:64); the doctor names it. (4) `ssh-keygen -Y` absent on old Windows OpenSSH; verify degrades to FAIL with the unlock, never to skip. (5) A runtime without `SubagentStart` loses the child's start line until its first tool call; the fallback is recorded in the doctor output. (6) A crashed child holds its lanes for up to 15 minutes; `octo ps --release` is the operator's early out.

Decisions:
1. New `KERNEL` category in rules.schema.json:31, or reuse ARCHITECTURE/FLOW/META? Default: reuse; a category is a schema PR with zero enforcement gain.
2. Signing: `ssh-keygen -Y` with allowed-signers files (verified offline here, OpenSSH 9.6p1) or minisign? Default: ssh-keygen; the `octorato-release` private key stays with the operator, only its public line ships; adopters add principals in `company/config/pkg-signers`.
3. Manifests for the 233 existing skills: generate `skill.json` for all of them in one mechanical PR before the cut (default), or grandfather with a doctor WARN? Default: generate; a standing WARN at the cut contradicts the release claim. Grandfather only if the generator hits a measured blocker (a skill with no parseable front matter gets a hand-written manifest).
